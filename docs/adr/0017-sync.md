# 0017 — Sync: a folder you already sync, and what travels in it

Status: **accepted — shipped, extended 2026-08-03**
Date: 2026-08-03 (original mechanism BACKLOG #62)
Relates to: [0010](0010-knowledge-base-second-brain.md) (KB / Onyx vault),
[0014](0014-scribe-handwritten-notebooks.md) (Scribe),
[0009](0009-password-manager-and-autofill.md) (the vault — deliberately *not* synced).

## Context

Flux has no server and no account. Sync therefore rides on a folder the user
already replicates — Syncthing, Dropbox, iCloud Drive, a USB stick. The transport
is untrusted by construction, which decides the crypto; what it does *not* decide
is what travels, in what form, or how two versions reconcile. Those are the
decisions worth recording, because several are counter-intuitive and two of them
have already caused real data problems.

## Decision

### Two transports, chosen by content

| | Transport | Why |
|---|---|---|
| Bookmarks, sessions, history, tasks, calendars | **`flux-sync.enc`** — one AES-256-GCM blob | Sensitive; small; benefits from being one atomic unit |
| Onyx vault, Scribe notebooks | **Plaintext files in a shared folder** | Large, file-per-item, and *mergeable* |

The split is not inconsistency. A monolithic encrypted blob defeats block-level
deduplication: `seal()` draws a fresh nonce per write, so identical plaintext
produces entirely different ciphertext and the sync tool re-transfers the whole
file. That is acceptable for a few hundred KB of bookmarks and fatal for a folder
of notebooks. Plaintext files also merge *per file*, which the blob cannot.

**The password vault is not synced at all**, by either route.

### The key comes from the passphrase **and the blob's salt**

The salt is stored in the clear in the blob header — you need it to derive the
key, and it is not secret. This is what makes "same passphrase, same key" work
across devices with no coordination.

**It also creates the sharpest hazard in the system.** A device that unlocks
while the folder is still empty mints a *fresh* salt and derives a different key
from the same passphrase. It then publishes a blob the other device cannot open,
and cannot open the other's. Same passphrase, no error, two permanent identities.
This is exactly what happens when a second device is set up before the file-sync
tool has delivered the first device's blob.

It **cannot be prevented** — "first device ever" and "the file hasn't arrived
yet" are genuinely indistinguishable from inside. So unlock reports when it mints
a new identity and the UI says what to do. Making a silent failure loud is the
whole available fix.

### Merge is additive, with tombstones

Union by a **content key**, never by id — ids are per-device counters and mean
nothing across machines. Bookmarks key on url+folder, sessions on name, tasks on
list+title, calendar feeds on URL, events on date+time+title, Scribe pages on
page id within a notebook, session tabs on workspace **name**.

Deletion propagates by tombstone (`key → deletion ms`); an item is suppressed
when a tombstone for its key is at least as new as the item. Re-adding with a
newer timestamp wins again — a tombstone is not a permanent ban on a key.

**Where a per-item timestamp exists, the newer edit wins.** Tasks gained
`updated_ms` specifically for this: without it an additive union skips a task it
already has, so ticking a box would never propagate and `done` would freeze at
whatever the first device published. **Where no timestamp exists, the existing
copy is left alone** — local calendar events have no per-event time, so letting
whichever device synced last overwrite the other's wording would be worse than
keeping each device's own.

### Idle syncs write nothing

The payload is hashed **before sealing** — the plaintext is stable across runs,
the ciphertext never is — and the push is skipped when the digest is unchanged.
Without this, auto-sync rewrote the entire blob every 180 seconds whether or not
anything had changed, which the sync tool then re-transferred in full.

## Consequences

- Not a CRDT and does not claim to be. Field-level conflicts don't merge: rename
  the same bookmark differently on two devices and neither wins — the union sees
  the key present and skips.
- Each device pulls before it pushes, so the concurrent-write loss window is
  bounded to changes made between one device's read and its write. Conflict files
  produced by the sync tool are **ignored** by Flux; they signal that two devices
  are syncing simultaneously, not that data needs hand-merging.
- The key is never persisted. Sync is idle after every restart until the
  passphrase is entered — deliberate, and a real friction worth revisiting if an
  opt-in keychain option is wanted (the vault already does this).
- Adding a store to the blob means adding a content key, tombstones, and — if its
  items are editable — an `updated_ms`. Skipping the last one produces a store
  that syncs creations and silently ignores edits.
- History has no tombstones on purpose: deleting history is a local privacy act,
  not something to propagate to every device.
